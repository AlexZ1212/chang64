### 2. Cloudflare Pages file-count crisis, fixed by redesigning static pages
Old architecture: **one static HTML page per puzzle** (`build_site.js`/`content.js`). Fine at 1779 puzzles (3558 pages). At 51 638 puzzles -> **103 398 pages**, `index.html` 14.2 MB (whole bank inlined into the puzzle-solving JS). Cloudflare Pages caps at 20k files (free) / 100k (paid) -- this would not even deploy.
Fix, in two parts:
- **Static pages**: replaced 1-page-per-puzzle with **13 category example pages** (one per theme: Winning capture, Double attack, Skewer, Mate in two, Winning move, Knight fork, Mate in one, Back-rank mate, Pin, Pawn fork, Deflection, Quiet move, Mate in three -- user originally said 10, corrected to 13 mid-session, all 13 now covered), each showing 3 hand-picked examples (easy/medium/hard, by diff percentile within the theme) with a real explanation grounded in `classify()`'s `explain` field (never invented), a "try it" link, and solution reveal. **148 total content pages now** (was 103 398), 433 sitemap URLs, site weight 45-55 MB depending on OG images.
- **Puzzle data loading**: the 51 638-puzzle bank is no longer inlined in `index.html`. `build_site.js` now writes `site/data/level-{1..10}.json` (~1.5-2 MB each), `site/data/puzzle-index.json` (id->level, for resolving a specific id without loading a whole level), `site/data/theme-counts.json` (tiny, for the theme filter dropdown), `site/data/rush-pool.json` (curated <=400-per-theme sample for Chang Sprint, so Sprint never needs the full bank). Client-side (`ui.js`/`ui2.js`) loads these **lazily, on demand**, same pattern as the pre-existing `loadOpeningBook()` (callback-based self-retry on missing data, not async/await -- kept consistent with the codebase's existing style). Result: **`index.html` 14.2 MB -> 287-298 KB**. A typical "open Resoudre" session downloads ~1.3-2 MB (one level), not 16 MB.
  - **Known, hard limitation**: this lazy-loading needs a real HTTP(S) origin. Opening `site/index.html` via `file://` (double-click) breaks puzzle loading entirely (CORS blocks `fetch()` from `file://`). This was ALREADY true before this session for the openings book (same fetch pattern, just a less noticeable failure -- opening name stays blank instead of the whole puzzle feature failing). For local testing: serve `site/` with any static server, never open the file directly.

### 3. Puzzle theme-classification bugs found and fixed (user spotted one by hand: "Enfilade #2K1VT" was actually a plain queen capture)
- **classify() ordering bug**: captures were checked AFTER pin/skewer detection in one code path, so a move that both captured a piece AND happened to align through/behind another piece got labelled Pin/Skewer instead of Winning capture. **4661 puzzles fixed** (all from the new mining batch -- the original 1779 bank was already correct, confirming the fix HAD already been applied there in a prior session, just not carried into the fresh `mine_puzzles.js` copy the user's machine used for the big mining run).
- **New: "exploited pre-existing pin" detection.** User specifically asked for this ("c'est tout l'interet des exercices"). Previously `classify()` only recognised a pin/skewer if the SOLUTION MOVE ITSELF created the alignment -- the extremely common "the defender is already pinned, so I just take what it was guarding" pattern was invisible, falling into generic "Winning capture". Added `absolutePin()`/`pinnedDefenderOf()` helpers to both `gen_puzzles.js` (`classify()`) and `gen_puzzles_v2.js` (`classifyBase()`), checking BEFORE the move whether the piece defending the captured square is itself absolutely pinned to its king. New `explain` shape for this case: `{captured:{sq,piece}, pinned:{sq,piece}, behind:{sq,piece:'k'}}` (vs the "pin created by the move" shape `{from,pinned,behind}` -- both handled in `content.js`'s `exampleExplanation()` and `ui.js`'s `explainSentence()`, distinguished by presence of `.captured`). **506 more puzzles recovered.**
- **Relative-pin detection gap**: the "skewer without king" branch of `classify()` only ever returned "Skewer" (front piece >= back piece value), NEVER "Pin" -- meaning the very common "knight pinned in front of a queen" pattern (not involving the king) was mislabeled Skewer or fell into "Winning move". Fixed to mirror the same value-based Pin/Skewer split already used for the king-branch. **327 more recovered** (290 from "Winning move", 37 from mislabeled "Skewer").
- Net effect: **Pin 191 -> 1024** (5.4x) across all three fixes combined. Deflection (see below) is separate.
- **Deflection, real fix (not just relabeling)**: root cause was that `mine_puzzles.js` NEVER builds multi-move "gain" sequences (always `sol.length===1` for non-mate puzzles) -- so `classifyQuiet()` (which needs `line.length>=3` to detect deflection) could never fire on ANY mined puzzle. All 5 pre-existing Deflection puzzles were from the old self-play-generated bank, none from mining. Also found `classifyQuiet()` itself had an inverted colour filter (checked what a piece was ATTACKING, not DEFENDING -- backwards from its own code comment) -- fixed, but that alone made the detection rate WORSE (30%->64% false-positive rate on a test sample) because "this piece defends something, somewhere" is true in nearly any busy position and proves nothing about whether deflection is the actual point of the puzzle. **Real fix**: tightened the check so it only fires when the FINAL move of the (retroactively-extended, 3-ply) sequence actually lands on the square the deflected piece was guarding. Detection rate on samples dropped to a much more plausible ~10-20 out of ~200 tested. Retroactively extended 3683 existing single-move "quiet" gain puzzles (2 more plies via `search()`, cheap: ~2 min for the whole set), found 444, robust-audited down to **437 applied** (`n` and `sol` rewritten to the 3-move sequence, `type` stays "gain"). **Deflection: 5 -> 442.**
- **Level rebalancing** (user: "at 1400 elo I wouldn't expect this many plain captures"): confirmed real -- some "Winning capture" puzzles (literally "take the free queen") were landing at level 9-10 purely because the position was cluttered with distractors, not because the pattern itself is hard. Capped Winning capture at level <=5 (5-way percentile split on its own diff distribution), then re-binned the REST of the bank (31 144 non-capture puzzles) into a full 1-10 spread on ITS OWN distribution, so levels 6-10 stay well-populated with genuinely-scaling themes rather than getting thin. Levels 1-5 now ~7213 each, 6-10 ~3114 each (down from ~5164 flat, but level 10 now has **zero** trivial captures -- verified).
- **Mate in three (61 total) and Winning capture's remaining volume (20 494) -- NOT touched, flagged not fixed.** Mate-in-3 is either genuinely rare in casual games or under-detected by insufficient search depth during mining (couldn't determine which without re-mining with deeper search, which needs new source game data Claude doesn't have). Winning capture's total volume was discussed (option to cap total count, not just level) but user didn't want to decide yet -- bank stays at 51 638, no cap applied to raw count, only to level ceiling.

### 4. Critical engine bug: threefold repetition never actually worked
User: "j'ai eu un cas avec 3 repetitions de position, pas de partie nulle." Reproduced with a hand-built move sequence (knight shuffle Nc3-Nc6-Nb1-Nb8 x2) -- `posCounts` for the repeated position never rose above 1, even on the third visit. Root cause: `makeMove()` called `bump(-1)` on the position being LEFT (correct for temporary probing inside `moves()`'s legality check, since `undoMove()` symmetrically restores it -- but WRONG for a real, permanent move: it erased the "this position occurred" memory every single time a real move was played, so a later real return to that exact position could never see a count >1). **Fixed in both `engine.js` and `engine_browser.js`**: `makeMove()` now only increments the arriving position, never decrements the one being left; `undoMove()` only decrements what it's undoing, never re-increments (nothing to compensate for any more). Verified: hand-built repetition sequence now correctly reaches count 3 and `isDraw()`/`isRepetition()` fire at the right move, `perft(4)` from the start position still returns the exact known value (197 281) -- no regression to move generation. This was a **pre-existing bug, not something introduced this session** -- likely present since the repetition-tracking code was first written, just never triggered by prior automated testing.

### 5. Multi-move "gain" puzzles broke the solving UI (found during full-site audit, after Deflection above went live)
Every "gain"-type puzzle (`type!=="mate"`) unconditionally finished (`finishPuzzle()`) after the FIRST correct move, regardless of `puzzle.sol.length` -- fine when every gain puzzle was single-move (true until this session), broken the moment Deflection puzzles (`sol.length===3`, `n===2`) existed: the player was never asked for the second move, and the forced opponent reply was never played. **Fixed** in `ui.js`: added a `puzzleSolPly` counter, `currentSolutions()` now checks `puzzle.sol[puzzleSolPly]` specifically (was: any entry in the array, which happened to work by luck for single-move puzzles but wasn't ply-aware), `tryPuzzleMove()` now continues the sequence (playing the KNOWN forced reply directly from `puzzle.sol`, not via `search()` -- deterministic, since the mined line already establishes it) instead of always finishing after move 1. Also fixed `loadAndRevealSolution()` (ui2.js -- used by BOTH the Sprint mistake-review feature and the new daily-puzzle calendar) which had the same one-move-only assumption; now replays the full `puzzle.sol` array directly. Verified end-to-end: full play-through of a real Deflection puzzle (move 1 -> auto-played forced reply -> move 2 -> correctly finishes), hint/solution-reveal mid-sequence (correctly targets whichever move is next), direct link to a multi-move puzzle (`#puzzle=id`) -- all confirmed working via a real headless-browser run, not just code review.
**French explanation text had a gender-agreement bug** in the live app (not the static pages, which were already correct): "la dame... force... il ne peut plus aider" -- hardcoded masculine regardless of the actual piece. Fixed in `ui.js`'s `explainSentence()` (Deflection and Pin-exploit cases), verified correct across ~40 real examples spanning all 6 piece types.

### 7. Daily puzzle calendar (new feature, user-requested + detailed)
`prog.dailyLog` (`{"YYYY-MM-DD": true}`, one entry per day the daily puzzle was solved -- no distinction between "never attempted" and "attempted but failed", both just unmarked). Recorded in `finishPuzzle()` (ui.js) when `won && puzzle.daily`. Two render surfaces sharing one `renderCalendarGrid(containerId, monthOffset, opts)`:
- Compact widget in the progress screen (`#calWidget`, current month only, no nav), right after the badges section.
- Full standalone page (`#pane-calendar`, its own "mode" alongside Explore/Legal/Prefs -- NOT a top-nav tab, reached via a link from the widget and from `setMode("calendar")`), with month prev/next navigation (capped so you can't navigate into the future).
Clicking a solved day calls `viewDailyArchive(dateKey)`: resolves that date's puzzle id via the exact same day-index formula as `dailyPuzzle()` (`Math.floor(Date.UTC(y,m,d)/86400000) % ids.length`, `ids` = `Object.keys(PUZZLE_INDEX)` in original insertion order -- this ordering guarantee matters, don't change how `puzzle-index.json` gets written without checking this), then `loadAndRevealSolution()` (same function Sprint-mistake-review uses) to show it fully solved.
Month/weekday names are hardcoded FR/EN arrays (`MONTH_NAMES`, `WEEKDAY_SHORT` in ui2.js), matching the existing convention elsewhere in the codebase (`fmtDate()` in the rating-graph code) rather than `Intl.DateTimeFormat`. Language switch mid-navigation preserves the currently-viewed month (a `calFullOffset` module-level variable, reset to 0 only on fresh navigation TO the calendar page via `setMode`, not on a same-page language-triggered re-render) -- this was a real bug found and fixed during testing, not designed right the first time.
Colour: brass/gold (`var(--brass)`, the same colour already used for unlocked badges) -- user explicitly asked for yellow instead of the originally-proposed green.

## KEY GOTCHAS / TRAPS (carried over + new this session)
- engine_browser.js piece encoding, TDZ risk from script-concatenation order (i18n, engine, pieces, ui, ui2, ui3) -- unchanged, still applies, see prior handoffs.
- `search(g,depth,timeMs)` is TIME-boxed not depth/node-boxed -- same as before, still the reason robust-audit re-checks exist.
- **New**: `bash_tool` calls do NOT share state -- a background process (`nohup ... &`) started in one call is dead by the next call. Long jobs (the 50k-puzzle audit, the deflection extension) had to be either chunked across many short synchronous calls (~2-4 min each, tool has an undocumented but real ceiling somewhere around 250-350s) or run fully synchronously within a single call when short enough.
- **New**: `npm install <pkg> --no-save` in this environment appears to reset `node_modules` to ONLY the newly-requested package when there's no `package.json`/lockfile present -- installing puppeteer-core silently wiped a previously-installed `terser`, breaking the next build until reinstalled. Install everything needed in one `npm install a b c --no-save` call, not sequentially.
- **New**: opening `site/index.html` via `file://` breaks puzzle loading (see architecture note above) -- always serve over HTTP for any local testing, including a Puppeteer run.
- **New**: `puzzle.sol` is now NOT always length 1 for `type:"gain"` puzzles (Deflection: length 3, `n:2`). Any future code touching puzzle-solving flow must not assume single-move gains again -- this exact assumption is what broke Deflection puzzles this session (see section 5).
- **New**: `classify()`/`classifyBase()`'s `explain` field shape now varies WITHIN the "Pin" theme (pin-created-by-the-move vs pin-already-existing-and-exploited -- distinguished by presence of `.captured`). Any code rendering `explain` for Pin/Skewer needs to branch on this, in both `content.js` (static pages) and `ui.js` (`explainSentence()`).
